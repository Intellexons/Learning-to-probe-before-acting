\noindent\textbf{What this is.}
A dated log of experiments run on the LoRA4VR self-play loop. Each entry
records what was tried, what happened, and how to reproduce it. Entries are
added as experiments complete. Reproduction references a git commit; the code
at that commit is the exact code that produced the result.

\noindent\textbf{System.} \texttt{Qwen2.5-Coder-3B-Instruct} fine-tuned with
GRPO/DAPO on a Google Cloud L4 GPU (24\,GB). The loop generates
\texttt{policy(state) -> action} Python code, scores it by running the policy
in a sandboxed environment, and trains LoRA adapters on the reward signal.

\section*{2026-04-13 \quad Environment design and first training runs}
% ============================================================

\commit{d96f7cb} $\cdot$ \textit{puck-on-tilted-plane env, runs 1--3}

\subsection*{Motivation}

CartPole was the original seed task but it is trivially solved by a two-line
bang-bang policy, giving a flat learning curve from iteration 0. Any standard
RL benchmark (LunarLander, Pendulum, MountainCar) is heavily represented in
the base model's pretraining data, so improvement from LoRA would be
confounded with prior knowledge. We need an environment the model has to
\emph{read} rather than recall.

\subsection*{The puck environment}

A puck moves in a bounded $[-6, 6]^2$ arena under a constant hidden tilt
$(t_x, t_y)$ and linear drag $\mu$. The policy receives
$\{p_x, p_y, v_x, v_y, g_x, g_y\}$ and must drive the puck to the goal
within 120 steps. Hidden parameters --- tilt, drag, thrust limit $a_{\max}$,
initial velocity --- are sampled per scenario from a seed and are not in the
state dict. The tight thrust envelope ($a_{\max} = \|tilt\|_2 \times 1.05 +
\epsilon$) ensures that a naive ``thrust straight at the goal'' policy
fails because it cannot cancel tilt drift.

\textbf{Reward:} $-\Delta t \cdot \text{dist}(p, g)$ per step; $+50$ bonus
on reaching the goal. Errored episodes score $-200$ per scenario (floor).

\textbf{Baseline gap} (200 seeds, hand-written policies):
\begin{itemize}[nosep]
  \item Naive aim: $\approx 26\%$ goal rate
  \item PD + tilt feedforward: $\approx 73\%$ goal rate
\end{itemize}

This gap is real headroom for LoRA to exploit.

\subsection*{Bugs encountered and fixed}

Three bugs had to be resolved before any learning was possible.

\textbf{Run 1 --- OOM on L4.}
Default config ($G=16$, batch 16, max completion 900 tokens) ran out of
memory at the backward pass. Fix (PR \#6): halved $G$ and batch to 8,
trimmed completion length to 600.

\textbf{Run 2 --- Reward sign flip.}
Training ran but degraded (fewer running samples each iteration). Errored
samples scored $0.0$ while samples that ran and drifted integrated large
negative rewards ($\approx -280$). GRPO's normalized advantage placed the
$0.0$ errors \emph{above} the mean, so the trainer rewarded broken code.
Fix (PR \#7): errored scenarios score $-200$, making broken code strictly
the worst outcome.

\textbf{Run 3 --- Dead advantages.}
With LR $= 10^{-5}$ and only 1 training prompt (4 gradient steps per outer
iteration), $\approx 75\%$ of batches were uniformly errored
(advantage $= 0$, no gradient). On the remaining steps, weight deltas were
$\sim 10^{-6}$ --- indistinguishable from zero. The reward was identical to
7 decimal places at iteration 0 and iteration 9. Fix (PR \#10): LR bumped
$10\times$ to $10^{-4}$; epochs raised to 20 (20 gradient steps per outer
iteration on 1 prompt).

\subsection*{Reproduce}

Commits: OOM fix \commit{ef228fe}, reward floor \commit{ef7e0c9},
LR/epoch fix \commit{e9353d7}. Env source: \texttt{scripts/seed\_tasks/puck\_tilted\_plane\_env.py}.

\section*{2026-04-18 \quad Run 5 probe: base model vs.\ 5 iterations of GRPO}
% ============================================================

\commit{d5bc81c} $\cdot$ \textit{puck\_grpo\_run\_5, iters 0 and 5, $n=20$ samples each}

\subsection*{Setup}

Run 5 used the config at \commit{e9353d7} (LR $= 10^{-4}$, $G=8$, 20 epochs
per outer iteration, DAPO loss, $\beta = 0$). It completed 5 outer iterations
before the VM was stopped. Adapter checkpoints were recovered to
\texttt{models/lora/puck\_grpo\_run\_5/}.

To inspect what the model actually writes, we sample 20 policies from the
base model (iter 0, no adapters) and from the trained model (iter 5), score
each against 8 scenarios, and compare. The tool is
\texttt{scripts/probe\_generation.py}; it saves per-sample policy files,
a summary CSV, and per-scenario reward breakdown to
\texttt{data/probe/\{run\_name\}\_iter\{N\}\_t\{temp\}/}.

\midrule
Iter 0 (base) & 13 / 20 & 7 / 20 & $-218.9$ & $-92.4$ \\
Iter 5        & 20 / 20 & 0 / 20 & $-140.4$ & $-140.4$ \\
\bottomrule

\subsubsection*{Iter 0}

The base model generates varied PD/PID controllers but crashes 35\% of the
time by attempting to read hidden env internals (\texttt{a\_max}, \texttt{dt},
\texttt{steps}) from the state dict. The 13 successful policies span a reward
range of $[-92, -373]$ with genuine variation in gain choices. The best
policy uses asymmetric gains ($k_{px}=2.0, k_{dx}=1.0$; $k_{py}=1.5,
k_{dy}=1.0$) and scores $-92.4$ over 8 scenarios.

\subsubsection*{Iter 5}

Zero crashes. The error-reading habit is gone. However, all 20 samples at
temperature $0.8$ produce \emph{exactly} $-140.3516$ (identical to 4 decimal
places). Every policy is byte-for-byte the same: $k_p = 2.0$, $k_d = 1.5$.
This is the \textbf{illustrative example embedded in the prompt template}
(\texttt{configs/prompt\_template.txt}). The model has memorized and
reproduced it verbatim.

\subsection*{Interpretation}

Training achieved two things and failed at a third.

\textit{Achieved.} Error rate dropped from 35\% to 0\% --- the model learned
not to read hidden env attributes. Mean reward over runners improved by 35\%.

\textit{Failed.} The model collapsed to a single policy. With $\beta = 0$
(no KL penalty), one training prompt, and 20 gradient steps per outer
iteration, GRPO found the prompt example as a high-reward fixed point and
reinforced it into a delta distribution. By iter 5, temperature $0.8$
sampling produces zero diversity. The best reachable policy is now $-140.4$,
worse than the base model's best ($-92.4$).

This is reward hacking: the model optimized the training distribution
(memorize the example) rather than the environment.

\subsection*{Hypotheses to test}

\begin{enumerate}[nosep]
  \item \textbf{Remove or paraphrase the prompt example.} It is the attractor
        GRPO is collapsing to. A deliberately suboptimal or absent example
        removes the fixed point.
  \item \textbf{More training prompts.} With 1 prompt, every outer iteration
        trains on the same input. Adding 4--8 tasks with varied dynamics forces
        generalization.
  \item \textbf{Raise $\beta > 0$.} A non-zero KL coefficient prevents the
        policy from drifting too far from the base distribution and preserves
        diversity.
  \item \textbf{Reduce epochs.} 20 gradient steps on 1 prompt per outer
        iteration is aggressive. 5--10 may preserve more exploration.
  \item \textbf{Probe at every intermediate checkpoint.} Does collapse happen
        at iter 1 or gradually? One probe per checkpoint would pinpoint when
        diversity dies.
\end{enumerate}

\subsection*{Open questions}

\begin{itemize}[nosep]
  \item What does the W\&B reward curve look like across the 5 iterations?
        (The run at \texttt{puck\_grpo\_run\_5-orchestrator} has data but some
        post-resume steps may be missing due to a step-monotonicity issue.)
  \item What is the PD+feedforward ceiling expressed in probe-script reward
        units? This would establish what score a successful LoRA policy needs
        to beat.
\end{itemize}

\section*{2026-04-19 \quad Run 8: removing the prompt example unlocks genuine learning}
% ============================================================

\commit{7ce5526} $\cdot$ \textit{puck\_grpo\_run\_8, 28 outer iterations, iters 0/4/8/12/16/20/24/27 probed ($n=20$ each)}

\subsection*{Setup}

Run 7 (aborted at iter 1) confirmed the model was already generating diverse
policies without the prompt example. Run 8 ran the full 30-iteration schedule
on the same config as run 5 (\commit{e9353d7}), with the single change that
the illustrative $k_p=2.0$, $k_d=1.5$ example was removed from
\texttt{configs/prompt\_template.txt} (PR \#13, \commit{e5fe162}). Adapters
were downloaded from the GCP VM and placed in
\texttt{models/lora/puck\_grpo\_run\_8/}. Eight evenly-spaced iterations
were probed to capture the full learning trajectory without evaluating all 28.

\subsection*{Results}

\centering

\toprule
\textbf{Iter} & \textbf{Crashes} & \textbf{Mean reward} & \textbf{Best reward} \\
\midrule
0  & 17 / 20 & $-1403$ & $-223$ \\
4  &  0 / 20 & $-221$  & $-165$ \\
8  &  0 / 20 & $-69$   & $-64$  \\

goal reaching (goal bonus $= +50$ per scenario).}
\end{table}

\begin{figure}[h]

\caption{Run 8 learning curve: mean and best reward across 8 probed iterations ($n=20$ samples each).
Generated by \texttt{scripts/analyze\_probe.py --run\_name puck\_grpo\_run\_8}.}
\end{figure}

\subsection*{Interpretation}

This is the first run showing genuine learning. Three phases are visible.
\textit{Iters 0--4}: crashes drop from 85\% to 0\% as the model learns the
valid state-key constraint. \textit{Iters 4--16}: reward improves steadily
from $-221$ to near zero — the model is reaching the goal on some scenarios
but not consistently. \textit{Iters 16--20}: a sharp transition to positive
reward ($+199$ mean), indicating consistent goal reaching across most scenarios.
The curve flattens after iter 20 with marginal gains through iter 27.

The single change responsible is the removal of the prompt example. In run 5
the example provided a ready-made fixed point that GRPO collapsed to after
one update. Without it, the model must explore the policy space, and GRPO
has real variance to amplify.

The iter-27 best reward of $+248$ approaches the hand-written PD+feedforward
ceiling (estimated at $\approx +270$ for 8 scenarios at $+50$ goal bonus each,
assuming $\sim 73\%$ goal rate from the 200-seed baseline).

\subsection*{Hypotheses / next steps}

\begin{enumerate}[nosep]
  \item \textbf{Probe all 28 iterations} to pinpoint exactly when the phase
        transition at iter 16--20 occurs and whether it is sharp or gradual.
  \item \textbf{Measure diversity at convergence.} Run 5 collapsed to 1 unique
        policy; does run 8 maintain diversity at iter 27, or does it collapse
        to a different fixed point once reward saturates?
  \item \textbf{Compare against the hand-written ceiling.} Score the PD+feedforward
        baseline with \texttt{scripts/probe\_generation.py} at iter 0 to get
        a reward number in the same units.
  \item \textbf{Train longer or with more prompts} to see whether the plateau
        at iter 20--27 is a capacity limit or simply convergence of the single
        training task.
\end{enumerate}

\section*{2026-04-22 \quad Policy analysis: what run 8 learned, and why iter 0 failed}
% ============================================================

\commit{e6bc200} $\cdot$ \textit{manual probe inspection, run 8 iter 0 and iter 27}

\subsection*{Setup}

With run 8 showing genuine learning (mean reward $+215$ at iter 27, up from $-1403$ at iter 0),
the question was: what strategy did the model actually discover, and why was the base model unable
to write a working policy at all? All 20 iter-0 and all 20 iter-27 policy files from
\texttt{data/probe/puck\_grpo\_run\_8\_iter\{000,027\}\_t0p80/} were read and compared manually.

\subsection*{Results}

\textbf{Iter 27 --- convergent velocity P-controller.}
Every iter-27 sample uses the same structural template: compute the angle to the goal, set a
desired velocity of magnitude \textit{speed} in that direction, and command acceleration proportional
to the velocity error:
\begin{equation*}
  a = \text{gain} \times (v_{\text{desired}} - v_{\text{current}})
\end{equation*}
The only variation across the 20 samples is in two scalar hyperparameters: desired speed (1.0--5.0)
and gain ($/0.05 = \times20$, $\times10$, $\times20$). The three below-average samples each have
a distinct defect: sample 08 contains a positional-step bug that degenerates to naive aim
(reward $-62.8$); sample 10 sets speed $= 1.0$, too slow to reach the goal in 120 steps;
sample 15 self-clips at $3.0$ below the env's own $a_{\max}$.

\textbf{Iter 0 --- API mismatch causes 85\% crash rate.}
17 of 20 base-model policies crashed with KeyError at reward floor $-1600$.
The specific hidden keys accessed are summarised in Table~\ref{tab:iter0_crashes}.
The three survivors avoided hidden keys only by accident: two hardcoded thrust magnitude constants
and one hardcoded all physics parameters (\texttt{tilt\_x = 0.0}, \texttt{mu = 0.5},
\texttt{a\_max = 1.5}). The survivors scored $-223$, $-312$, and $-325$ --- all worse than
the naive aim baseline.

\centering
\begin{tabular}{ll}
\toprule
\textbf{Hidden key} & \textbf{Samples accessing it} \\
\midrule
\texttt{a\_max} & 00, 01, 02, 03, 04, 05, 07, 08, 11, 12, 14, 15, 16, 19 \\
\texttt{tilt\_x}, \texttt{tilt\_y} & 01, 03, 04, 06, 08, 11, 12, 13, 14, 15, 16, 19 \\
\texttt{mu} & 01, 04, 07, 08, 12, 15, 16 \\
\texttt{dt} & 16, 17 \\
\bottomrule
\end{tabular}
\caption{Hidden state keys accessed by crashing iter-0 samples.}
\label{tab:iter0_crashes}
\end{table}

\subsection*{Interpretation}

\textbf{What iter 27 discovered.}
The trained model found a velocity P-controller rather than the PD-on-position + tilt-feedforward
strategy used by the hand-written baseline. This is structurally different: there is no
position error term and no tilt awareness. The approach works because high-gain velocity
tracking rejects tilt disturbances reactively within a few timesteps, yielding near-ceiling
reward without explicit feedforward. The residual 8\% gap to the hand-written ceiling
($+248$ vs.\ $\approx +270$) is consistent with reactive rather than proactive tilt rejection.

\textbf{Why iter 0 failed.}
The base model's prior --- drawn from pretraining on standard RL codebases --- is that a physics
simulation exposes all its parameters through the state dict or environment attributes. 14 of 17
crashing samples attempted tilt compensation or drag cancellation that would have been correct
if the hidden parameters were accessible. The model's control-theory knowledge was largely sound;
its environment-API assumption was wrong. GRPO fixed the API assumption without teaching better
control theory, because velocity tracking was sufficient to saturate the available reward.

\subsection*{Hypotheses / next steps}

\begin{enumerate}[nosep]
  \item \textbf{Probe the transition from position-thrust (iter 0 survivors) to velocity-tracking
        (iter 27).} At which iteration does the velocity-control template first appear?
        Checking iter-4 policies would show whether it emerges immediately after crash rate drops.
  \item \textbf{Test whether harder tilt distributions force tilt compensation.}
        With wider tilt ranges the reactive velocity-tracker may fail; GRPO would then need to
        discover an explicit feedforward term to push reward higher.
  \item \textbf{Provide the hidden parameters in the state dict and retrain.}
        If the base model already knows how to use tilt/drag/a\_max (most iter-0 samples attempt it),
        a single run with those keys exposed could achieve the hand-written ceiling immediately
        and reveal what further headroom exists beyond it.
\end{enumerate}

\subsection*{Open questions}

\begin{itemize}[nosep]
  \item Would the velocity-tracking template generalise to a new environment with different
        dynamics, or is it a memorised pattern for the puck task?
  \item The best iter-27 policy ($+247.6$) and the best iter-0 survivor ($-223$) both use
        only valid state keys. Is the iter-27 template a refinement of the iter-0 survivor
        template, or did it emerge independently under GRPO pressure?
\end{itemize}
